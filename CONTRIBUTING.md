# Contributing to Paperstand

Thanks for taking a look. Paperstand is small and opinionated; this file describes how to
get it running, what the checks are and what a change is expected to look like.

## Ground rules

- Everything in the repository — code, comments, documentation, commit messages — is
  written in **English**. The only translated text is the user interface, which lives in
  `frontend/messages/{en,it}.json`.
- Paperstand is **agnostic about where the PDFs come from**. It reads a folder. Never name
  a specific downloader, service or provider in code, configuration, documentation or test
  fixtures; describe file name shapes as "common real-world naming" instead.
- **Examples use fictional publications**, listed in
  [`docs/sample-library.md`](docs/sample-library.md), and never a real title or a real
  place. Each one exists for a parsing edge case; reuse them rather than inventing a name.
- The library is read-only. Nothing Paperstand does may write inside `/library`; everything
  it writes goes under `/data`.
- **No naming rule lives in code.** File name parsing is driven by the declarative profiles
  in `backend/paperstand/parsing/profiles/`. A shape the parser cannot read is a change to
  a profile, not an `if` in the engine.
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) —
  see below. Commits made with the help of a coding agent carry a `Co-Authored-By` trailer.

## Development setup

Requirements: Node 22+, Python 3.12+, [uv](https://docs.astral.sh/uv/), Docker (optional).

```bash
git clone https://github.com/smashkins/paperstand.git
cd paperstand
cp .env.example .env

make sample-library OUT=./library   # ~110 generated PDFs to develop against
make dev                            # API on :8000, frontend on :5173
```

The sample library is fake from cover to colophon — generated PDFs, fictional mastheads,
"SAMPLE LIBRARY · GENERATED CONTENT" printed on every page — and it exercises every layout
and naming shape the parser claims to handle. Develop against it rather than against your
own collection: a bug is much easier to report when the file that triggers it can be
regenerated by anybody.

The backend lives in `backend/` and is managed by uv (`backend/pyproject.toml`,
`backend/uv.lock`). The frontend lives in `frontend/` and is managed by npm. Both are
driven from the repository root through the `Makefile`.

## Make targets

| Target | What it does |
| --- | --- |
| `make dev` | API with autoreload plus the SvelteKit dev server |
| `make dev-api` | Backend only, on port 8000 |
| `make dev-web` | Frontend only, on port 5173, proxying `/api`, `/opds` and `/openapi.json` |
| `make test` | Backend pytest and frontend vitest |
| `make lint` | ruff, mypy, prettier, eslint, svelte-check |
| `make fmt` | Format the backend and the frontend in place |
| `make gen-api` | Export `openapi.json` and regenerate the typed API client |
| `make sample-library OUT=./library` | Generate the fake library |
| `make docker-build` / `make docker-run` | Build and run the container image |

## Checks

`make lint` and `make test` must be green before anything is committed; CI runs the same
commands, plus `npm run build` and a build of the container image.

Three of them catch mistakes that are easy to make and hard to see:

- **`make gen-api`.** `frontend/src/lib/api/openapi.json` and the TypeScript client
  generated from it are committed. CI regenerates both and fails on a diff, so a change to
  a request or a response model has to be followed by `make gen-api`.
- **The message check.** `npm run lint` in `frontend/` also runs `npm run i18n:check`, which
  fails when `messages/en.json` and `messages/it.json` disagree about their keys or their
  placeholders, and when user-visible text is written into a component instead of going
  through the catalogue. Every string the interface shows exists in both languages.
- **`make lint` is strict.** ruff with a wide rule set, mypy in strict mode over the
  backend, `svelte-check` over the frontend. None of it is advisory.

## Working on the parser

The parser is the part most likely to need a change, and the two commands that make it
tractable touch neither the database nor the cache:

```bash
# One line per PDF: the title, the date, and the rule that decided
uv run --project backend python -m paperstand parse-report ./library

# Every step taken on one file, in order
uv run --project backend python -m paperstand parse-explain ./library/<some file>.pdf
```

[`docs/parser-profiles.md`](docs/parser-profiles.md) explains the profile format and what
each rule identifier means. When you teach the parser a naming shape, add it to the fixture
table in `backend/tests/fixtures/filenames.py` as well: it is one row, and it is what stops
the shape regressing later.

## Commit messages

[Conventional Commits 1.0](https://www.conventionalcommits.org/): a type, an optional
scope, and a summary in the imperative, lower case, with no full stop.

```
docs(readme): add cover banner and badge row
build(docker): pin uv and trim the runtime image
```

| Type | For |
| --- | --- |
| `feat` | A new capability |
| `fix` | A bug fix |
| `docs` | Documentation only |
| `build` | The build, the image, the dependencies |
| `ci` | The workflows |
| `refactor` | A change that is neither a fix nor a feature |
| `perf` | A change made for speed |
| `test` | Tests only |
| `style` | Formatting only, no behaviour |
| `chore` | Anything else |

Scopes are the parts of the system: `api`, `scanner`, `parser`, `reader`, `storefront`,
`opds`, `docker`. Add a body when the *why* is not obvious from the summary, and a
`BREAKING CHANGE:` footer when an upgrade needs a hand — a renamed setting, a moved volume,
a cache that has to be thrown away.

## Pull requests

Describe what changed and why, keep the commits logical, and make sure `make lint` and
`make test` pass. A change to what the interface looks like is easier to review with a
screenshot; a change to parsing is easier to review with the `parse-explain` output from
before and after.

## Reporting bugs

Open an issue with the Paperstand version, how you run it (Docker or from source), the
folder layout of your library, and — when the problem is about the catalogue — a couple of
anonymised file names that are classified wrongly, plus the `parse-explain` output for one
of them.
